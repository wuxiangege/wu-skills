# Finance Center 示例词条（Agent 参考）

以下为 `finance-center-api` / `finance-center-jobs` 的压缩示例；对用户解释时按 SKILL.md 五维展开，可补充最新代码。

---

## 结算单（SettlementBill）

**分类**：业界+本项目定制

**是什么**：供应商在一段时间内、按结算规则汇总订单/售后后形成的**应付结算凭证**；本项目用状态机管理从建单到付款全生命周期。

**组成**：结算单头（供应商、周期、合作模式、结算模式）+ 源明细 + 结算结果明细；关联结算规则、付款流程。类型见 `SettlementBillType`：常规(0)、瑕疵品(1)、预览(10)。

**变化**：`SettlementBillStatus` — 待结算(10) → 结果同步完成(200) → 计算完成待提交(900) → 待审核(901) → 待付款(902) → 付款中(903) → 已完成(904)；可关闭/审核不通过。见 `ddd/enum/settlementbill.go` 的 `stateMachine`。

**解决问题**：把分散订单、促销、退货规则**算清应付金额**，并支撑审核与付款，避免人工 Excel 汇总。

**意义**：财务中心核心单据；`finance-center-jobs` 的 SettlementJob/CalculationJob 负责自动生成与重算。

**举例**：每月对寄售供应商 A 拉取上月出库订单 → 计算促销扣减 → 生成结算单 → 运营审核 → 财务付款。

**易混**：对账单（StatementBill）面向商旅双边订单核对，不是供应商货款结算单。

## 对账单（StatementBill）

**分类**：业界+本项目定制（商旅场景加重）

**是什么**：用于**商旅（TMC）**等场景，汇总「服务商侧订单」与「客户侧订单」并核对一致性的单据。

**组成**：对账单头 + 明细（卖方/买方订单，`DetailType`）；拆分维度 `ByBizEntity` / `ByCostCenter`；类型：以商旅订单为准(1) / 以客户订单为准(2)。

**变化**：单据状态：待提交(10) → 待审核(20) → 待结清(40) → 已结清(50)；核对状态 `CheckStatus`：待核对(10) → 核对中(11) → 异常(20) / 成功(30)。

**解决问题**：平台与客户、TMC 服务商之间**订单与金额不一致**时的对账与开票前置。

**意义**：差异类型见 `SBCompareResultDiffType`（缺失、价格异常等）；与结算单服务于不同业务线。

**举例**：企业客户月结机票 → 生成对账单 → 核对票面价/服务费差异 → 通过后进入开票/结清。

## 结算规则（SettlementRule）

**分类**：业界+本项目定制

**是什么**：约束「何时、按什么时点、什么合作模式」把订单纳入结算的配置契约。

**组成**：结算方式（先货后款/先款后货）、合作模式（经销/寄售）、匹配时点（下单/出库/确认收货）、赠品规则、品牌范围、生效周期与审核状态。

**变化**：待提交 → 待审核 → 已审核 → 未生效/已生效/已过期；创建结算单时按**审核时间取最新生效规则**（见 repository 注释）。

**解决问题**：不同供应商合同条款差异大，需可配置、可审计，避免结算口径漂移。

**意义**：SettlementJob 依赖规则拉取周期；规则错误会导致整批结算单金额错误。

## 毛保结算（SettlementMaoBaoMode）

**分类**：本项目/行业定制（零售毛利保护）

**是什么**：相对「常规结算」的另一种 `SettlementModeWay`：按**毛保比例**等约定结算，而非直接改「结算含税单价」。

**组成**：结算单上 `settlementMode=2`；修改结果明细时常规模式改单价、毛保模式改毛保比例（见 `modifyResultDetail.go` 校验）。

**变化**：与常规模式互斥修改字段；计算逻辑在 CalculationJob 分版本处理。

**解决问题**：品牌商与渠道约定的**保底毛利**结算，防止低价倾销侵蚀毛利。

**意义**：改错模式会导致明细修改接口报错或金额口径错误。

## 经销 / 寄售（CooperationMode）

**分类**：业界通用（合作模式枚举）

**是什么**：库存与货权归属不同的两种采购合作：经销(1) 一般买断库存；寄售(2) 库存归供应商，售出后结算。

**组成**：体现在结算规则、结算单头 `cooperationMode` 字段；影响结算周期与数据源。

**变化**：规则审核生效后影响后续自动结算；历史单不回溯改模式。

**解决问题**：统一系统内多种供应链合作方式的结算口径。

**意义**：寄售常见于美妆/免税；结算作业 README 写明支持寄售、自采等模式。

## 开票上传申请（uploadApply / FileUploadStatus）

**分类**：本项目内部命名 + 业界「批量开票」概念

**是什么**：用户上传账单文件（如火车/机票明细）后，经校验、解析、开票、推送的**异步任务聚合单**。

**组成**：主单状态 `FileUploadStatus`（draft → verifying → parsing → invoicing → invoiced…）+ 子文件/子任务；按产线聚合（openspec 中 Single 模式）。

**变化**：验证 → 解析 → 开票 → 部分成功/失败；火车换开等场景有特殊统计规则（单测注释）。

**解决问题**：大批量差旅发票不能逐张手工录入，需流水线校验与开票。

**意义**：与 `InvoiceBill`（发票账单解析核对）链路衔接；状态字符串为英文枚举，对接前端与 MQ。

## 付款申请（PaymentApplication）

**分类**：业界通用（付款审批单）+ 本项目状态码

**是什么**：结算审核通过后，发起对外付款的审批单据。

**组成**：状态 `DRAFT` → `PENDING_REVIEW` → `APPROVED` → `COMPLETED`；与结算单状态「待付款/付款中」联动。

**变化**：见 `paymentapplication.go` 的 `ValidNextStatus`。

**解决问题**：付款与结算分离，满足内控与银企对接。

**意义**：结算单到 902/903 后往往依赖付款申请闭环。

## 结算作业 / 计算作业 / 对账作业（Jobs）

**分类**：本项目内部（Job 命名）+ 业界「批处理」

**是什么**：`finance-center-jobs` 中定时任务：SettlementJob 建单、CalculationJob 算金额、CheckingJob 比平台与供应商数据。

**组成**：cron + 分布式锁 + 调 finance-center-api；依赖价格中心、订单、ERP 等。

**变化**：按 `CyclePullingIntervalMinutes` 等配置周期执行；计算有 v1/v2 版本。

**解决问题**：人工无法日清海量订单的结算与对账。

**意义**：API 管状态与人工操作，Jobs 管自动化；排查问题需两边日志对照。
