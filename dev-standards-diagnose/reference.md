# Development Standards

本规范用于代码 review 和 PR 自检。默认约束新增代码和本次修改代码；历史代码不因本次未触达而阻塞，但被修改区域应按规范收敛。除明确豁免外，`MUST` 是合并门禁，`SHOULD` 是强建议，偏离时需在 PR 中说明原因、风险和补偿措施。

## 1. 接口限制与输入处理

- MUST: 所有列表接口必须设置服务端分页上限，单页最大 `1000` 条；未传分页参数时必须使用默认值，禁止返回全量数据。
- MUST: 批量接口必须限制单次处理数量，默认不超过 `1000` 条；超过时分批处理。
- MUST: 查询接口中的字符串字段在校验和查询前必须去除前后空格；全空白字符串按空值处理。
- MUST: 新增或修改接口字段必须保持向前兼容；新增字段默认可选，禁止删除、重命名或改变已上线字段类型、语义和路径。
- MUST: 导出类接口必须使用分页、游标或流式处理，禁止一次性加载全量数据。
- MUST: 外部回调、消息消费、定时任务、导入、重试写入和批量写入必须有幂等保护。
- MUST: 幂等方案必须明确幂等 key、去重存储位置、并发下的原子性保障，以及重复命中时的返回行为。

## 2. 代码结构与复杂度

- MUST: 禁止无语义魔法值；业务数字、状态、配置 key、错误码应抽取常量。
- MUST: 同一字符串重复超过 3 次必须抽取常量。
- MUST: 单函数圈复杂度不得超过 25；核心业务函数 SHOULD 控制在 15 以内。
- MUST: 单个业务函数不超过 50 行；超过时拆分校验、查询、转换、持久化等步骤。
- SHOULD: 状态机、金额计算、跨系统字段转换应集中封装，避免分散条件判断。

## 3. 类型、命名、注释与生成代码

- MUST: 字段、变量、函数名必须表达清晰业务含义，避免单独使用 `data`、`info`、`flag`、`type` 等含糊命名。
- MUST: API 请求/响应字段必须有注释；go-zero DTO 注释维护在 `.api` 定义中，手写外部 client DTO 注释维护在源 struct 中。
- MUST: DB model 字段必须有注释，说明业务含义、单位、枚举来源或特殊取值。
- MUST: 枚举值必须有注释，说明业务含义和适用场景。
- MUST: API DTO、DB model、配置结构体、消息体、事件体、回调 payload、导入导出行结构和业务领域实体中禁止使用 `interface{}` / `any` 字段，必须使用明确类型。
- MUST: 禁止使用 `map[string]interface{}` / `map[string]any` 承载业务数据；确需开放 KV 时使用 `map[string]string`、`map[string]int64` 或明确 value struct。
- MUST: 禁止使用数组下标、列表顺序或游标偏移承载业务语义；跨数组、跨列表、跨接口返回的数据关联必须使用业务唯一键，例如 `id`、`code`、`sn`、`uuid`。
- SHOULD: 行为依赖可以使用小接口，例如 repo/client 抽象；接口必须表达具体能力，禁止空接口和大而全接口。
- EXEMPT: 第三方原始 payload、历史兼容字段、未解析 JSON 可短期使用 `json.RawMessage` 或明确豁免，但必须说明解析位置、校验规则和迁移计划。
- MUST: 内部函数使用小驼峰，公共函数使用大驼峰。
- SHOULD: 函数名短且表达动作，例如 `validatePageSize`、`buildPreBillItems`。
- SHOULD: 核心函数、复杂分支、兼容逻辑和跨系统转换需要简短注释，解释原因而不是复述代码。
- MUST: `.api`、Wire 或 Swagger 相关生成文件禁止手改，包括 `internal/types/types.go`、`internal/handler/routes.go`、`di/wire_gen.go`。

## 4. 测试质量

- MUST: `logic/`、`worker/`、`task/`、`dao/` 中承载业务分支、状态变更、外部调用或持久化逻辑的函数必须有单测。
- MUST: 单测覆盖核心链路、失败链路和边界 case，例如空数据、超限、重复请求、外部服务失败、DB 失败。
- MUST: 新增或修改核心逻辑的覆盖率达到 80%；未达到时需在 PR 说明原因和补偿验证。
- SHOULD: mock 外部依赖时验证关键入参和错误处理，避免只断言“不报错”。

## 5. DB 与事务

- MUST: 查询必须命中合适索引；新增或修改大表查询条件时，PR 需说明索引依据，必要时附 `EXPLAIN`。
- MUST: 禁止无分页扫表。
- MUST: 禁止在 `for` 循环中逐条查询或逐条写入 DB；使用批量查询、批量写入或预加载。
- MUST: N+1 查询、无分页大表扫描、全表扫描和无限循环属于高危红线，必须在合并前修复或给出明确的业务豁免与补偿方案。
- MUST: 单次批量 DB 操作不超过 `1000` 条。
- MUST: 涉及状态流转、金额、库存成本、结算单和批量写入时，必须明确事务边界和失败补偿策略。
- MUST: 分页查询必须有稳定排序字段，避免翻页重复或漏数据。

## 6. 金额、精度与状态

- MUST: 金额、税率、比例、成本等核心计算禁止使用 `float` 承载；必须明确单位、精度和舍入规则。
- MUST: 单据状态、任务状态、结算状态应集中定义；状态迁移必须可读、可测。
- SHOULD: 对外展示字段和内部持久化字段命名不一致时，应显式转换并覆盖测试。

## 7. 文件与导出

- MUST: xlsx 写入必须使用流式写入，禁止在内存中构建完整数据后一次性写入。
- MUST: 大文件导出必须分批查询、分批写入，并控制单任务内存占用。
- MUST: 临时文件必须在任务结束后清理；失败任务需要记录可定位状态。
- SHOULD: 文件名、sheet 名和导出字段集中定义，避免硬编码散落。

## 8. 日志、外部调用与安全

- MUST: 与外部服务交互必须记录结构化日志。
- MUST: 写入类请求记录请求参数和返回摘要；列表类请求只记录请求参数和必要统计，禁止完整打印大响应。
- MUST: 错误必须记录日志，并包含业务单号、任务 ID、租户、批次号、外部系统名等关键定位信息。
- MUST: 日志禁止输出 token、密钥、密码、完整手机号、身份证号、银行卡号等敏感信息。
- MUST: 外部服务调用必须设置超时；重试必须有次数上限；外部写入重试前必须确认幂等。

## 9. PR 自检与豁免

- MUST: PR 描述包含业务变更、影响服务、生成文件、测试命令和结果。
- MUST: 涉及接口字段、列表、批量、导出、DB 查询、外部调用、动态字段或 model 字段变更的改动，说明向前兼容、分页上限、批量上限、索引依据、日志、幂等、字段注释和类型边界处理。
- EXEMPT: 生成代码、纯 DTO、简单常量定义、测试 case 数据和非本次修改的历史代码可豁免部分复杂度或覆盖率要求。
- EXEMPT: 任何豁免都需要写明原因、风险、补偿措施和是否需要后续任务。

## 10. 自动化与人工检查

- MUST: 每个任务完成前必须执行 `make qa-check`；失败项必须修复，告警项和人工 checklist 必须在 PR 或交付说明中确认。
- SHOULD: 可自动检查的规则优先接入 lint、CI 或脚本，例如函数复杂度、重复字符串、字段注释和覆盖率。
- MUST: 暂未自动化的规则进入 PR checklist，由 reviewer 核对业务边界、幂等、索引、日志脱敏和事务边界。
